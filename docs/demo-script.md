# Demo script (4 to 5 minutes)

> **Status note (9 November 2026).** This is the local recording guide from 7 November. The deployed instance is https://travis.nodesemesta.com, where the provider keys are configured. Where a screen still returns a structured error, say so; do not present it as live.

Skrip demo dalam bahasa Inggris dengan satu baris narasi Indonesia per adegan (ID).

This script follows what works in the repository today. Read "What needs which key" before you record, because three screens depend on keys that were empty when this repository was validated (HERE, OpenWeather) and one depends on a Bright Data search that has not yet returned events.

**Do not present anything as live that is not.** If a screen shows a structured "not configured" or "no result" message, say so on camera. That honesty is part of the product (no invented data).

## 1. Preparation (before recording; say in the video that data was prepared)

Clean state, from the repository root:

```bash
supabase start
supabase db reset --yes
npm run bootstrap:local
```

Edit `.env.local` (git-ignored) and fill in the keys you have: `BRIGHT_DATA_API_KEY`, `BRIGHT_DATA_SERP_ZONE`, `BRIGHT_DATA_UNLOCKER_ZONE`, `VULTR_INFERENCE_API_KEY`, `HERE_API_KEY`, `OPENWEATHER_API_KEY`. For local email also set `EMAIL_PROVIDER=smtp`, `EMAIL_FROM`, `SMTP_HOST` (container address from `docker inspect supabase_inbucket_vultr`) and `SMTP_PORT=1025`. Set the email variables after the last `bootstrap:local`, because bootstrap does not preserve them.

Then start three terminals:

```bash
npm run build
npm run start:api:local        # terminal 1
npm run dev:web:local          # terminal 2: http://localhost:3000
npm run start:worker:local     # terminal 3: needed for invoice generation, email, alerts
```

Open Mailpit in a second browser tab: `http://127.0.0.1:55424`.

Demo login: `DEMO_EMAIL` and `DEMO_PASSWORD` from `.env.local` (the password is generated by bootstrap and is not in the repository).

Seed data: trip "Jakarta Business Trip" (12 to 14 November 2026, Asia/Jakarta), places Hotel Indonesia Kempinski, Jakarta Convention Center and Soekarno-Hatta International Airport. **The seed has no journey leg.** Mobility and the departure reminder need one, so:

1. Sign in, open **Trips**, scroll to **Add a journey leg**.
2. From: Hotel Indonesia Kempinski. To: Jakarta Convention Center. Departure: a time a few hours from now (local time of the trip). Optional "Arrive by" a bit later. Click **Add journey leg**.

You can do this on camera in Scene 9 order, or before recording. If you do it before, say so.

Optional warm-up (disclose it): run the event search of Scene 3 once before recording. The result is stored for 6 hours (`EVENT_DISCOVERY_TTL_HOURS`), and the identical search in the video then returns the stored result without a provider call. The result view shows its retrieval time. The search itself can take from several seconds to a minute or more.

## 2. What needs which key

| Scene | Needs | Without it |
|---|---|---|
| 1 Login, 2 Trip and places | Local Supabase | Does not run |
| 3 Event search | Bright Data key and zones, Vultr key | Structured error "not configured" (HTTP 503). With keys: a list of events, **or** "No matching events yet", **or** a provider error. A live list of events has not been obtained so far |
| 4 Booking and dummy payment | An event card (from Scene 3) | No card, nothing to book. See backup A |
| 5 Invoice and email | Worker running; for email, local SMTP settings (Mailpit) | Invoice can be generated by hand without the worker. Email stays pending without the worker |
| 6 Assistant | Vultr key | "Summarize my trip" and "My recommendations" work with the Vultr key only. Events need Bright Data. Weather, restaurants and routes need OpenWeather and HERE |
| 7 Mobility | `HERE_API_KEY` (routes, traffic, restaurants), `OPENWEATHER_API_KEY` (weather), Bright Data (activities) | Structured "not configured" errors. Nothing is invented |
| 8 Alerts | Worker running; a journey leg departing in the next 24 hours. The departure reminder calls no provider. Traffic and weather alerts need HERE and OpenWeather | Reminder works. Traffic and weather jobs fail visibly under "Background checks" |
| 9 Trips | Local Supabase | Does not run |

Verified-by-test is not the same as verified live. HERE, OpenWeather and Resend have never been called with a real key in this repository. Bright Data has not returned a usable event list.

## 3. Scenes

Times are targets. Total about 4:30 to 5:00.

### Scene 1: Login (0:00 to 0:20)

1. Open `http://localhost:3000`. The sign-in card shows "Go further. Feel at home."
2. Email is prefilled with `demo@travelflow.local`. Type the password and click **Sign in**.

ID: "Login memakai Supabase Auth. Travis tidak pernah meminta data kartu."

### Scene 2: Trip and context point (0:20 to 0:45)

1. The top bar shows **Active trip: Jakarta Business Trip**. The sidebar lists the views: Explore and book, Mobility, Assistant, Itinerary, Alerts, Invoices, Trips.
2. In **Choose a context point**, click **Jakarta Convention Center**. A check mark appears. Hotel and airport are listed too; a place that is not resolved shows "Needs confirmation" and cannot be chosen.

ID: "Semua pertanyaan terikat ke trip dan titik konteks, jadi pengguna tidak mengulang detail."

### Scene 3: Find events (0:45 to 1:30)

1. In **What is happening nearby?** leave Category `business_events`, Date `2026-11-12`, From `18:00`, Until `23:00`. Click **Find nearby**. The button shows "Searching…".
2. Narrate what happens in the backend: Bright Data search, pages read through Web Unlocker, events checked against the page, stored with source and time.
3. Possible outcomes, all legitimate:
   - Event cards. Open **Source and freshness** on one card to show provider, freshness, retrieval time and **Open source**.
   - **No matching events yet**. Open **About this search** and read the limitations (for example unreadable Google redirect links). Say that nothing was invented.
   - A red error banner (provider rejected or unavailable). Say that there is no fallback and no fake result.
4. The Explore form uses a fixed `+07:00` offset, so it is correct for Jakarta only.

ID: "Event hanya muncul bila halaman sumber memuat tanggal dan jam yang cocok. Jika tidak, sistem berkata tidak ada."

### Scene 4: Booking and dummy payment (1:30 to 2:20)

Only if Scene 3 produced a card (otherwise use backup A or B).

1. Click **Review booking** on a card. The right panel **INTERNAL BOOKING** shows "Demo event price" with the total, tax, and `demo-pricing-v1`, and the text "No real money moves". Say that the server decides the price.
2. Click **Confirm booking details**. Status shows "pending payment".
3. In **DUMMY PAYMENT** click **Pay successfully**. The panel shows **Booking confirmed** with a confirmation code and a **View invoice** button.
4. For the failure path (optional, 20 seconds): click **Find nearby** again (the stored result is reused, so there is no new provider call), choose a card, click **Confirm booking details**, then **Simulate failure**. The panel shows **Payment failed** and no confirmed state.

ID: "Booking baru menjadi confirmed setelah dummy payment sukses. Kegagalan pembayaran tidak pernah menghasilkan booking confirmed."

### Scene 5: Invoice and email (2:20 to 3:00)

1. Click **View invoice** (or open **Invoices**). The invoice card shows booking reference, payment status, total.
2. With the worker running, the invoice is created automatically after a successful payment (`INVOICE_AUTO_GENERATE=true`). If it is not there yet, click **Generate invoice**.
3. Click **Download PDF**. Open it briefly: invoice number `INV-YYYY-NNNNNN`, amounts equal to the booking.
4. In **Email this invoice** type an address and click **Send invoice**. The delivery list shows the status. Switch to Mailpit and show the message with the PDF attached.
5. Say: email is sent through local SMTP (Mailpit). Resend (production) has not been tested. An email failure does not change the booking or payment.

ID: "Invoice PDF disimpan di bucket privat dan dikirim sebagai lampiran setelah checksum cocok."

### Scene 6: Assistant (3:00 to 3:40)

1. Open **Assistant**. In **Place to ask about** keep **Whole trip** or choose a place.
2. Click **Summarize my trip**. The answer comes from stored trip data. Show a card and the **About this answer** disclosure.
3. Click **My recommendations** (shows stored recommendations; may be empty).
4. If keys are present: click **Weather here**, **Restaurants nearby**, or use the **From** / **To** selectors and the route button. Each card shows its source and retrieval time. A route card marked "Recommended by Travis" is chosen by the backend engine, not by the model.
5. If a key is missing, the assistant shows a structured error ("No answer was made up"). Show it.
6. Say: the model plans and writes text; the backend runs the tools and rejects answers whose numbers or ranking do not match the data. Changes to the itinerary require a confirmation dialog.

ID: "LLM hanya merencanakan dan menulis. Angka dan peringkat berasal dari backend."

### Scene 7: Mobility (3:40 to 4:10)

1. Open **Mobility**, section **Compare ways to travel**. **Journey leg** shows the leg you created. Optionally tick **Live traffic** and **Weather**.
2. Click **Compare routes**.
   - With `HERE_API_KEY`: option cards labelled **Recommended** or **Alternative** show time, cost (or "Cost unavailable"), walking, transfers, safety buffer, deadline result and the suggested departure. Click **Select this route**.
   - Without it: a structured "not configured" error. Say that HERE has not been verified live here.
3. In **Weather and traffic**, **Refresh weather** and **Refresh traffic** need their keys too.
4. In **Activities and restaurants**, **Type** and **Find nearby**: activities use Bright Data and can take up to a minute; restaurants use HERE.

ID: "Mesin rute deterministik: urutan dan angka tidak bisa diubah oleh model."

### Scene 8: Alerts (4:10 to 4:30)

1. Open **Alerts**. With the worker running and a leg departing within 24 hours, a departure reminder appears ("Time to head to ..."), with **What we found** and **What you can do** separated and a **Source and freshness** disclosure.
2. Click **Mark as read**, then **Dismiss**.
3. Under **Background checks** show the jobs. A failed weather or traffic job (no key) is shown as failed, not hidden. **Run again** creates a new job.

ID: "Alert hanya di dalam aplikasi, dibuat dari data yang belum kedaluwarsa."

### Scene 9: Trips (4:30 to 5:00)

1. Open **Trips** (**TRIP SETUP**). Show **Create a trip** (button **Create trip**), the trip list, **Add a place**, **Add an agenda item**, **Add a journey leg**, and **Timeline so far**.
2. Optionally open **Itinerary** to show **Timeline**, **Recommendations** (**Add recommendation**, **Save for later**, **Dismiss**) and **Activity log**. Say that the assistant never changes the itinerary without a confirmation.
3. Close with the architecture in one sentence: Vultr Serverless Inference for the model, Bright Data for live web data, Supabase with Row Level Security for data, one VM on Vultr as the deployment target. **Say that the deployment has not been done yet** if that is still true.

ID: "Target deployment: satu VM Vultr dengan Docker Compose. Belum di-deploy pada saat dokumen ini ditulis."

## 4. Backup steps (these are not runtime fallbacks)

The application has no fallback: a failed provider is an error. The steps below change how you prepare or record the demo, and they must be disclosed.

- **A. Run the demo from a server with a fixed IP.** Bright Data rejected some pages from the development network. Running the API from a Vultr VM (once deployed) or any host with a stable IP might change that. This is **not verified**. It has not been tried, because no server access exists yet.
- **B. Booking flow on a labelled fixture.** If no live event is available, run the scripted browser test, which starts its own API and a fixture Bright Data stand-in that returns schema.org Event markup: `node --env-file=.env.local scripts/ui-golden-path.mjs`. It writes screenshots to `docs/validation/ui-golden-path-*.png`. Show those or screen-record that script's browser, and state clearly in the video: "events in this part come from a test fixture, not from Bright Data". Do not edit the database by hand to create events.
- **C. Provider keys for Mobility, weather, traffic.** Obtain `HERE_API_KEY` and `OPENWEATHER_API_KEY` before recording. If you cannot, show the structured error. The screenshots `docs/validation/ui-assistant-fixture-providers-*.png` show route and weather cards from labelled provider fixtures; if you show them, say they are fixture data.
- **D. Record in separate takes.** Event search can take up to a minute. Record it as its own take, keep the real waiting time or cut it with a visible note, and do not splice in results from another run.
- **E. Time budget.** If the video must stay under five minutes, skip the failure path in Scene 4 and the Itinerary view in Scene 9.

## 5. Reset between takes

```bash
supabase db reset --yes
npm run bootstrap:local
```

This deletes all local data, including bookings, invoices and stored event results. Sign in again, re-add the journey leg, and re-set the email variables in `.env.local` if bootstrap removed them. Restart the API and the worker if they report errors after the reset.
